# /abandoned

Find leftover BigQuery tables and GCS export JSON that the current pipeline no longer produces, and give the user the commands to delete them. **Never run the delete commands yourself.** The user reviews and runs them.

The user may pass `test` or `prod` (default: both, test first) and optionally a dataset name.

## Step 1 — Run the script

From the repo root with the venv active:

```bash
source .venv/bin/activate
python scripts/find_abandoned.py --env test > /tmp/abandoned-test.txt 2>&1
python scripts/find_abandoned.py --env prod > /tmp/abandoned-prod.txt 2>&1
```

Add `--dataset <name>` when the user named one. It reads BigQuery and GCS via Application Default Credentials and workflow runs via `gh`, and can take a few minutes for all datasets.

## Step 2 — Report

Per environment, give:

- A short table: dataset, abandoned tables, abandoned JSON groups.
- Datasets the script **skipped** (no successful DAG run on record) in one line. They weren't checked.
- The **"Still read by frontend/src"** list, called out prominently. These are excluded from the commands because the frontend still requests them, which usually means the frontend points at a renamed or moved dataset and is serving frozen data. Offer to file an issue for each distinct case.

## Step 3 — Hand over the commands

Point the user to the `# Delete commands` section of `/tmp/abandoned-<env>.txt` and suggest running them dataset by dataset, test before prod. Remind them:

- Dropped tables are recoverable for 7 days via BigQuery time travel; deleted JSON is not (bucket versioning is off), but any JSON a live table produces is regenerated by rerunning its DAG.
- `gcloud`/`bq` may need `gcloud auth login` first.

Do not paste hundreds of command lines into chat; summarize counts and point to the file.
